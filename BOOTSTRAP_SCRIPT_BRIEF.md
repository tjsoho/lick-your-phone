# Brief — Build a One-Command Bootstrap Script

**Repo this lives in:** `summer-website-template` (the GitHub template repo).
**Audience:** the next Claude Code session working in that repo.
**Goal:** the owner runs **one command from anywhere on their machine** and ends up with a fully working clone — GitHub repo created, Supabase project provisioned with schema + buckets + admin user, Vercel project linked and deployed, env vars wired, browser open at the live URL.

---

## The single command (user experience)

```bash
npx create-summer-site
```

That's it. No clone step. No copying env vars by hand. No SQL editor.

The script runs interactively and asks for:

1. **New repo name** (e.g. `acme-corporate-site`) — used as the GitHub repo name, the local folder, the Vercel project name, and the Supabase project name.
2. **Admin password** for `toby@ai-guy.co` (default email; allow override with `--admin-email`).
3. **Supabase region** (default `ap-southeast-2 Sydney`, allow list pick).
4. **Vercel team / scope** (default personal account, allow list pick).

Everything else is automated. Total wall time ≈ 4–6 minutes (Supabase provisioning is the slow step).

At the end the script prints:

```
✓ Repo:       https://github.com/<user>/<name>
✓ Supabase:   https://<project-ref>.supabase.co
✓ Vercel:     https://<name>.vercel.app
✓ Admin URL:  https://<name>.vercel.app/admin/login
✓ Local:      cd <name> && npm run dev
```

…and opens the deployed URL in the default browser.

---

## How `npx create-summer-site` resolves

This template repo ships a small CLI package that GitHub-creates the repo from the template, clones it locally, then runs the rest of the bootstrap inside the new clone.

Two paths to consider — recommend the second:

### Option A — Publish to npm

`package.json` declares a `bin: { "create-summer-site": "./scripts/bootstrap.mjs" }` and is published to npm under the name `create-summer-site`. Then `npx create-summer-site` Just Works. Cleanest UX, but requires npm publishing + maintenance.

### Option B — Run via `gh` (RECOMMENDED for v1)

No npm publish needed. The user runs:

```bash
gh repo create my-site --template tjsoho/summer-website-template --clone --private \
  && cd my-site && npm install && npm run bootstrap
```

…or wrap that in a one-liner alias. We can also ship a tiny **`bootstrap.sh`** at the repo root that does the GitHub-repo-create + clone + cd + `npm install` + `npm run bootstrap` — the user just downloads/curls that one file:

```bash
curl -fsSL https://raw.githubusercontent.com/tjsoho/summer-website-template/main/bootstrap.sh | bash -s my-site
```

**Build Option B first.** Add a clear note in the README that v2 will publish to npm for `npx`.

## What the bootstrap script does, step by step

Implementation lives at `scripts/bootstrap.mjs` (Node 20+, ESM, no TypeScript build step). The script is **idempotent where possible** — if a step has already run successfully, skip it.

### 0. Preflight checks
- `node --version >= 20`
- `gh --version` present and `gh auth status` shows logged in (else `gh auth login`)
- `vercel --version` present (else install via `npm i -g vercel`)
- Internet reachable

### 1. Collect inputs (interactive prompts)
Use `@inquirer/prompts` (or `prompts` — smaller). Ask:
- Repo name (validate: kebab-case, no spaces, ≤ 50 chars)
- Admin email (default `toby@ai-guy.co`)
- Admin password (hidden input, validate length ≥ 12)
- Supabase region pick list
- Vercel scope pick list
- Confirm summary before running

Cache long-lived credentials at `~/.summer-website-template/config.json` (Supabase Personal Access Token, Vercel API Token). On first run, prompt for them with a link to the generation page; on subsequent runs, reuse.

### 2. Create GitHub repo from template (only in Option A path)
If we're already inside a cloned new repo (Option B), skip. Otherwise:
```
gh repo create <name> --template tjsoho/summer-website-template --private --clone
cd <name>
npm install
```

### 3. Provision Supabase project
Hit `POST https://api.supabase.com/v1/projects` with:
```json
{
  "name": "<repo-name>",
  "organization_id": "<from /v1/organizations>",
  "plan": "free",
  "region": "<chosen>",
  "db_pass": "<auto-generated, captured for the env>"
}
```

Poll `GET /v1/projects/{ref}` until `status === "ACTIVE_HEALTHY"` (typically 60–180s). Show a spinner with elapsed seconds.

Capture:
- `project_ref` → becomes `NEXT_PUBLIC_SUPABASE_URL = https://<ref>.supabase.co`
- Anon key from `GET /v1/projects/{ref}/api-keys` → `NEXT_PUBLIC_SUPABASE_ANON_KEY`
- Service role key from same endpoint → `SUPABASE_SERVICE_ROLE_KEY` (script-only, NEVER ship to client)

### 4. Apply database schema
The repo ships `setup-database.sql` (already in the template). Apply it via the Supabase SQL endpoint or by piping it into `psql` using the connection string from `GET /v1/projects/{ref}/config/database`.

Recommended: `pg` npm package + `client.query(sqlContents)` in one transaction. Wrap in a try/catch so partial failure shows what broke.

### 5. Create storage buckets
Use `@supabase/supabase-js` server-side with the service role key:

```js
await supabase.storage.createBucket("site-images", {
  public: true,
  fileSizeLimit: "50MB",
  allowedMimeTypes: ["image/*"],
});

await supabase.storage.createBucket("site-files", {
  public: true,
  fileSizeLimit: "50MB",
  allowedMimeTypes: ["application/pdf"],
});
```

The image bucket name (`site-images`) is what the existing media library code already references. Don't change it.

### 6. Apply storage RLS policies
The buckets need policies so the admin panel can upload. Either:
- (a) bake them into `setup-database.sql` already (preferred), or
- (b) issue them as separate SQL statements from the script.

Verify by uploading a tiny test file and reading it back. Delete the test file when done.

### 7. Create admin user
With the service role key:
```js
await supabase.auth.admin.createUser({
  email: adminEmail,
  password: adminPassword,
  email_confirm: true,
});
```

The `email_confirm: true` skips the verification email — admin can log in immediately. If the email already exists (idempotent re-run), log it and continue.

### 8. Seed default pages
The fallback content in `src/app/*/​_config.ts` shows up when no DB row exists. But the admin panel writes rows the moment someone saves a page. To make the new site **show the dummy content out of the box**, optionally insert one row per page using the fallback data:

```js
for (const slug of ["home", "about-us", "who-we-help", "property-managers",
                    "corporate-teams", "services", "contact", "faq", "footer"]) {
  const fallback = await import(`../src/app/${pathFor(slug)}/_config.ts`);
  await pgClient.query(
    "INSERT INTO pages (slug, title, description, content) VALUES ($1, $2, $3, $4) ON CONFLICT (slug) DO NOTHING",
    [slug, fallback.title, fallback.description, fallback.content]
  );
}
```

Mark this **optional**. If complex to import the _config files from the script, just leave the DB empty and rely on the fallback rendering until the admin hits Save.

### 9. Write `.env.local`
Create `.env.local` (gitignored) at the repo root:

```env
NEXT_PUBLIC_SUPABASE_URL=https://<ref>.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=<anon>
SUPABASE_SERVICE_ROLE_KEY=<service>     # used by admin server-actions, NEVER exposed
SUPABASE_DB_PASSWORD=<generated>         # for future migrations
```

### 10. Create Vercel project + push env
```js
// vercel CLI is more reliable than the API for project linking
execSync(`vercel link --yes --project ${name} --token ${vercelToken}`);
execSync(`vercel env add NEXT_PUBLIC_SUPABASE_URL production preview development --token ${vercelToken}`);
// repeat for each env var
```

Or use the API directly: `POST https://api.vercel.com/v9/projects` then `POST /v9/projects/{id}/env`.

### 11. Initial deploy
```
vercel deploy --prod --token <token>
```

Capture the deployment URL.

### 12. Push the bootstrap result back
The script may have generated files (e.g. nothing meaningful unless you opted into seeding). If anything new was created in the repo, commit + push so the new GitHub repo reflects the bootstrap state.

### 13. Print summary + open browser
Print the URLs (format shown at top of this brief). Use the `open` package to open the deployment URL in the default browser.

## External services & tokens needed

| Service | What's needed | Where to get it | Where to store it |
|---|---|---|---|
| **GitHub** | `gh` CLI authed | `gh auth login` (already done) | n/a |
| **Supabase** | Personal Access Token | https://supabase.com/dashboard/account/tokens | `~/.summer-website-template/config.json` |
| **Vercel** | API Token | https://vercel.com/account/tokens | same |

The script prompts for the Supabase + Vercel tokens **once** on first run, validates them, then caches. Subsequent runs skip those prompts.

## Out of scope (do NOT build in v1)

- Custom domain configuration (user can do via Vercel dashboard after)
- Email/SMTP setup for password reset (Supabase ships its own)
- CI/CD beyond Vercel auto-deploy
- npm publishing of the CLI (do in v2)
- Multi-environment (staging/prod split) — single production env only
- Multiple admin users — just `toby@ai-guy.co`
- Image migration from another Supabase project

10. ☐ Upload an image in the admin media library → confirm it lands in `site-images`
11. ☐ Delete the test repo + Supabase project + Vercel project after verifying

If any step fails the script should print exactly which one and offer to roll back cleanly (delete Supabase project, delete Vercel project, delete GitHub repo) so the user can re-run from scratch.

## Error handling principles

- **Each step is its own function with try/catch** — failure prints the step name and the error, then asks "Retry / Skip / Abort?"
- **Retryable steps default to retry** (network blips happen)
- **Destructive steps are confirmed twice** (deleting a Supabase project on rollback)
- **Don't leak tokens to stdout** — redact in any error output
- **Write a `.bootstrap.log`** in the repo with full step-by-step state for debugging

## Implementation notes for the agent

- Use ESM only (`type: "module"` already in package.json)
- Pin dependency versions in `scripts/package.json` (separate from app's) — keeps the CLI footprint small
- Total CLI deps target: `@inquirer/prompts`, `chalk`, `ora`, `node-fetch` (or native fetch), `pg`, `@supabase/supabase-js`, `open`
- Keep total script size manageable — split files in `scripts/lib/` once any single file passes ~300 lines
- The Vercel CLI is more battle-tested than the API for the initial link/deploy — call it via `execa`. Reach for the raw API only for env var bulk-add (which is faster as a single API call)
- For password handling, **never echo it back**, **never write it to the log**, **store only the hash if you need to persist it** (you don't — it goes directly to Supabase via `auth.admin.createUser` and is forgotten)
- For the Supabase Management API: the token has full account access. Document this clearly. Recommend the user create a token scoped to a single org if possible.
